# Plan: Onboarding Bugfixes (Bugs 1.1 – 1.4)

**Domain:** Onboarding, Authentication, Shelters, Dashboard
**Priority:** 1 (P0 — login/registration crashes block new users)
**Status:** Draft
**Tracks:** Bug report §1 (Onboarding) + §5.1 note (checklist dismissal overlaps with 1.1; see plan 24)

---

## Overview

Four onboarding defects were reported. Two are **hard crashes** (1.3, 1.4) that block newly verified accounts from using the app; two are **UX gaps** (1.1, 1.2). This plan fixes all four. The checklist-dismissal feature reported as 1.1 and 5.1 is **one feature** and is fully specified here; plan `24_completed_checklist_dismissal_plan.md` tracks the enhancement framing and must not be implemented as separate work.

**Goals:**
- Newly verified Individual and Shelter accounts can log in and reach the correct onboarding flow without a 500 error.
- Users who complete onboarding can permanently remove the completed checklist from their dashboard.
- Users can review and edit previously submitted onboarding answers (with personality recalculation) instead of being dumped on the last question.

## Bug 1.3 + 1.4 — Crash after email verification / first login

### Problem

After creating an account, verifying the email, and logging in for the first time, the application crashes with:

```
ActionDispatch::MissingController
in Onboarding::Adopter::Individual::QuestionsController#show

uninitialized constant Onboarding::Adopter::Individual
```

This affects **both** Shelter accounts (1.3) and Individual accounts (1.4).

### Root Cause (confirmed in code)

1. `ApplicationController#after_sign_in_path` (app/controllers/application_controller.rb:75–95) sends **individual** (adopter) users with incomplete onboarding to:
   ```ruby
   onboarding_adopter_onboarding_questions_path
   ```
2. That helper is generated by the **legacy/broken** route block (config/routes.rb:57–60):
   ```ruby
   namespace :adopter, as: :adopter_onboarding do
     resource :questions, only: [ :show, :update ], controller: "individual/questions"
     resource :completion, only: [ :create ], controller: "individual/completions"
   end
   ```
   Rails resolves `controller: "individual/questions"` inside the `adopter` namespace to `Onboarding::Adopter::Individual::QuestionsController`, but **no such class exists** — the only controllers are:
   - `app/controllers/onboarding/adopter/questions_controller.rb` → `Onboarding::Adopter::QuestionsController` (legacy alias)
   - `app/controllers/onboarding/individual/questions_controller.rb` → `Onboarding::Individual::QuestionsController` (current)
3. `bin/rails routes` confirms: `onboarding_adopter_onboarding_questions` → `onboarding/adopter/individual/questions#show` (a controller that does not exist).
4. **Shelter users (1.3)**: the verified-login path itself uses `Onboarding::DetermineDestination` (correct → `/onboarding/shelter/questions`), but a shelter user can still be routed through `after_sign_in_path` from several call sites (landing redirect, `require_no_authentication`, the onboarding `require_onboarding_not_complete` redirect in `Onboarding::Shelter::QuestionsController#require_onboarding_not_complete`, etc.). The crash is triggered whenever the user lands on `after_sign_in_path`; the fix must make `after_sign_in_path` role-correct for every call site.

### Expected Behavior

- A newly verified **Individual** user logs in → lands on `/onboarding/individual/questions`.
- A newly verified **Shelter** user logs in → lands on `/onboarding/shelter/questions` (or `/shelters/new` if already onboarded).
- No 500, no `MissingController`, regardless of entry point (email-verification redirect, login form, landing-page redirect, profile page).

### Proposed Changes

1. **Fix the redirect target** in `ApplicationController#after_sign_in_path`:
   - Replace `onboarding_adopter_onboarding_questions_path` with `onboarding_individual_questions_path` for `adopter?`/`individual?` users.
2. **Fix or remove the broken legacy route** (config/routes.rb:57–60):
   - Preferred: delete the `namespace :adopter` block and all references to `onboarding_adopter_*` helpers, since "adopter" is a deprecated alias for "individual" (the login route `login/adopter` already 301-redirects to `login/individual`).
   - If legacy URLs must keep working (e.g., external links), remap the `adopter` namespace to the real controller: `resource :questions, only: [ :show, :update ], controller: "/onboarding/individual/questions"` (absolute controller path) and same for `completion`, then keep the helper alias.
3. **Remove/replace remaining `onboarding_adopter_*` references:**
   - `app/controllers/onboarding/adopter/*` (legacy controllers) — delete or leave as thin aliases only if step 2 keeps the route. Do **not** leave dead code that routes point at.
   - `app/views/onboarding/adopter/questions/show.html.erb` and its Stimulus wiring — superseded by the `individual` views; confirm the `individual` views are the ones rendered by the canonical `individual` routes.
4. **Harden `Onboarding::DetermineDestination`** to never return the adopter URL (it already returns `/onboarding/individual/questions` — keep, add spec).
5. **Add regression specs** (request specs per repo convention):
   - New verified individual + incomplete onboarding → login → `200` at `/onboarding/individual/questions`.
   - New verified shelter + incomplete onboarding → login → `200` at `/onboarding/shelter/questions`.
   - Verified individual completing onboarding → after-login redirect → dashboard (no `MissingController`).
   - Verified shelter completing onboarding → after-login redirect → `/shelters/new` or shelter dashboard.
   - Every route generated by `after_sign_in_path` / `DetermineDestination` resolves to an existing controller (`bin/rails routes` sanity check).

### Acceptance Criteria (1.3/1.4)

- **AC-1.3-1** Register a Shelter, verify email, log in → no 500; redirected to shelter onboarding.
- **AC-1.4-1** Register an Individual, verify email, log in → no 500; redirected to individual onboarding.
- **AC-1.4-2** An individual who already completed onboarding logs in → lands on dashboard (not the wizard).
- **AC-1.4-3** No code path references a controller constant `Onboarding::Adopter::Individual::*`.
- **AC-1.4-4** `bin/rails routes` contains no route mapping to a non-existent controller.

## Bug 1.2 — Shelter preference editing does not display previous answers

### Problem

Editing the shelter personality/preferences questionnaire (Settings → Edit Preferences → `profile_shelter_onboarding_path(from_profile: true)`) reopens the wizard at the **last question** instead of showing prior answers. Users cannot review or edit earlier responses. The same defect exists for the individual questionnaire (`profile_onboarding_path(from_profile: true)`).

### Root Cause (confirmed in code)

- `Onboarding::Shelter::QuestionsController#show` (and `Onboarding::Individual::QuestionsController#show`) compute:
  ```ruby
  @current_step = [ @profile.onboarding_step.to_i, 1 ].max
  ```
- A completed profile has `onboarding_step == TOTAL_QUESTIONS` (7), so the wizard renders only the **last** question. There is no review page, no per-question jump, and no edit-after-save path for earlier questions.

### Expected Behavior

Replacing the one-question-at-a-time wizard when `from_profile: true`, display a **Review page** that shows:
- Every question.
- The user's current answer.
- Support for all answer types: text, single choice, multi choice, and any future input types.
- The ability to edit one or multiple answers.
- Recalculation of the shelter personality after saving changes.

### User Story

> As a shelter owner (or individual adopter) who has completed onboarding,
> I want to review all my previous answers and edit any of them in one place,
> so that my profile stays accurate and my shelter personality updates accordingly.

### Proposed Changes

1. **Add a review page** rendered when `from_profile: true` (or a new `review` action):
   - Route: reuse `onboarding/shelter/questions#show` with `from_profile: true` (and same for individual) OR add `GET onboarding/shelter/questions/review`.
   - List every question from `Onboarding::Shelter::QuestionsData.all` / `Onboarding::Individual::QuestionsData.all` with the stored answer from `user.shelter_profile` / `user.individual_profile`.
   - Read-only display by default with an **Edit** affordance per answer (and an "Edit all" affordance).
   - Editing uses the existing `update` (`SaveResponse`) contract per question, then returns to the review page.
2. **Render answers per type** (component/partial per type, forward-compatible):
   - `text` → textarea, saved value pre-filled.
   - `single_select` → radio/select with the saved option marked.
   - `multi_select` → chips/checkboxes with saved options marked.
   - Future types: add partials in a `questions/` answer-type namespace; the review page iterates by `question[:type]`.
3. **Recalculate personality after save**:
   - Shelter: call `Onboarding::Shelter::Personality.call(profile)` and display the updated personality card on the review page.
   - Individual: recalc any equivalent derived display (readiness/onboarding display) as applicable.
4. **Backward navigation inside the wizard**: while keeping the linear wizard for first-time onboarding, when `from_profile: true` show a "Back to review" / "Review answers" action so users can return to the review list.
5. **i18n**: all new strings in `config/locales/{en,es}.yml` under `onboarding.shelter.review.*` and `onboarding.individual.review.*`.

### Acceptance Criteria (1.2)

- **AC-1.2-1** From Settings → Edit Preferences, a completed shelter user sees a review page listing **all** questions with current answers, not a single question.
- **AC-1.2-2** Each answer type (text, single, multi) renders its stored value correctly on the review page.
- **AC-1.2-3** Editing any single answer saves via the existing `SaveResponse` service and returns to review with the updated value.
- **AC-1.2-4** After saving changes, the shelter personality (badge/title) reflects the new answers.
- **AC-1.2-5** The same behavior works for the individual questionnaire.
- **AC-1.2-6** All strings are translated (en/es), no hardcoded user-facing text.

### Edge Cases

- Profile with `onboarding_step == 0` but answers present (partial save) → review shows answered + unanswered states; unanswered questions flagged.
- Array-typed answers (`multi_select`) saved as empty array → shows "no selection" state, not a crash.
- Question config changes between versions (e.g., new option added) → stored values not in the option list are preserved and marked "legacy value".
- User saves via the wizard's `update` while `onboarding_completed?` is true → must not wipe `onboarding_completed_at` (already guarded by `Complete`; add spec).

## Bug 1.1 + Enhancement 5.1 — Completed onboarding checklist cannot be dismissed

### Problem

After completing the shelter onboarding checklist (all 6 steps), the checklist section remains visible on the shelter dashboard indefinitely. It takes up space with no value once complete.

### Root Cause (confirmed in code)

- `app/views/shelters/dashboard/show.html.erb:43–54` always renders the checklist card.
- `app/views/shelters/dashboard/_checklist.html.erb` renders all steps and, when all are done, shows the "Live & Active" level + encouragement. There is **no dismiss/hide/clear action** and no persistence of a dismissed state.

### User Story

> As a shelter owner who has completed all onboarding steps,
> I want to dismiss the completed checklist so that my dashboard shows only the information I still need.

### Proposed Changes

1. **Add a dismiss action** (button: "Hide checklist" / "Dismiss") shown **only when all steps are done** (`done_count == total_count`), placed in the checklist card header (top-right).
2. **Persist dismissal** per shelter (server-side, so it survives sessions/devices):
   - Add `checklist_dismissed_at` timestamp on `shelters` (Data domain owns the migration) **or** a `ShelterSetting`/preference record — decide with Data agent; prefer a boolean/timestamp column on `shelters` for MVP simplicity.
   - Alternatively session-scoped dismissal is acceptable for MVP only if cross-device persistence is not required; default recommendation: persist on the model.
3. **Controller change**: `Shelters::DashboardController#show` skips rendering the checklist when `shelter.checklist_dismissed_at.present?` (or re-renders nothing in the card).
4. **Restore affordance**: show a subtle "Show checklist" link/footer once dismissed, in case the owner wants it back (cheap, prevents "I hid it and can't find it").
5. **i18n**: new strings in `config/locales/{en,es}.yml` (`shelters.dashboard.onboarding.dismiss`, `.restore`, `.dismissed_confirmation`).

### Acceptance Criteria (1.1 / 5.1)

- **AC-1.1-1** When all checklist steps are complete, a Dismiss/Hide action appears on the checklist card.
- **AC-1.1-2** Clicking it removes the checklist section from the dashboard and persists the choice.
- **AC-1.1-3** On subsequent visits, the completed checklist stays hidden.
- **AC-1.1-4** A restore/show action exists and brings the checklist back.
- **AC-1.1-5** While any step is incomplete, the dismiss action is not shown (checklist must remain to drive completion).
- **AC-1.1-6** No regressions to the progress bar / level-up / confetti behavior for incomplete checklists.

> **Note:** Bug 5.1 (Enhancement) describes the same feature. See `24_completed_checklist_dismissal_plan.md` — implement once, satisfying both.

## Success Metrics

- **Crash rate:** zero `ActionDispatch::MissingController` occurrences for `/onboarding/*` in logs after deploy (log alert).
- **Funnel recovery:** % of verified accounts reaching onboarding completion within 24h of signup does not drop; first-login 5xx rate = 0%.
- **Checklist dismissal:** % of fully-onboarded shelters that dismiss the checklist within 7 days of the feature shipping (track via `checklist_dismissed_at` presence).
- **Preference editing:** % of preference-edit sessions that change ≥1 answer (previously impossible), and reduced support/abandonment on the edit-preferences flow.

## Test Strategy

- Request specs for 1.3/1.4 routing (as listed in AC).
- Request spec for the review page: GET with `from_profile: true` renders all questions; PATCH of a single answer persists and recomputes personality.
- Request spec for checklist dismissal: POST dismiss → dashboard omits checklist; restore works.
- Feature-level manual QA script: register → verify → login (both roles); complete onboarding → dismiss checklist; edit preferences → review/edit answers → personality updates.

## Scope

**In scope:** routing/redirect fixes; review page for onboarding answers; checklist dismissal; related specs, locales, and design-system-consistent UI.

**Out of scope:** onboarding question content changes; personality algorithm changes (only recalculation on edit); notification-bell routing (tracked in plan 21); sidebar/navbar redesign (plans 22–23).

## Risks

- Removing the legacy `adopter` route could break bookmarked `/onboarding/adopter/*` URLs → keep a 301 redirect to `/onboarding/individual/*` if legacy URLs matter.
- Personality recalculation must not change existing saved profiles unless answers change — recalc only on save.
- Dismissal persistence adds a schema change — coordinate with Data agent; keep migration reversible.
